# 新会话开工提示词

> 用途：开启新会话继续开发时，把下面代码块整段粘进对话框即可，无需再解释背景。
> 配套文档：`AGENTS.md`（规则）、`docs/HANDOFF.md`（交接详情）、`docs/progress.md`（进度与证据）。
> **最后更新**：2026-09-12（第 2 组数据模型与迁移完工后）

## 主提示词（继续开发 W5）

```
你是 DocMind 项目的开发助手。按下面顺序开工，不要跳步。

【第一步 读文档】
1. AGENTS.md —— 项目规则、保护清单、停机点
2. docs/HANDOFF.md —— 交接文档：本机环境坑、已冻结决策、工件地图、模型网关实况、验收语料
3. openspec/changes/add-doc-ingest-pipeline/tasks.md —— 10 组 35 项周计划（1.1–1.6、2.1–2.2 已完成，带证据）
4. docs/progress.md 末尾的「第 2 组」一节 —— 上一组交付了什么、踩了什么坑
5. 需要背景时再读 specs/001-doc-ingest-pipeline/spec.md、docs/PROJECT_CONTEXT.md、docs/findings.md（D-017~D-027）

【第二步 环境（先照做，否则会误判）】
每条 Bash 命令开头都必须显式设置 PATH，否则 ls/grep/dirname 等 coreutils 全部 command not found：
export PATH="/d/Docker/App/resources/bin:/c/Users/ASUS/.workbuddy/binaries/PortableGit/versions/1.2.0/cmd:/c/Users/ASUS/.workbuddy/binaries/PortableGit/versions/1.2.0/bin:/c/Users/ASUS/.workbuddy/binaries/PortableGit/versions/1.2.0/usr/bin:/d/nvm/nodejs:/usr/bin:/bin"
要点：
- git.exe 在 PortableGit 的 cmd/ 而不是 bin/；docker.exe 在 D:\Docker\App\resources\bin
- 本机没有 curl、没有本地 PostgreSQL/psql，裸 python 也不在 PATH
  → HTTP 探针与脚本一律用 backend/.venv/Scripts/python.exe（Python 3.12.3）
  → 查库用 docker exec docmind-pg psql -U docmind -d <db> -c "..."（容器内有 psql）
- 仓库根 .venv（3.13.14）只用于生成验收语料，不要拿它跑后端
- 沙箱禁止写工作区外；依赖只能装项目内 venv
- docmind 栈已在跑：api / worker / beat / pg / redis / nginx 六容器（pg 宿主 5433、redis 6380、nginx 8080）
  查看状态：docker compose ps；改代码后需 docker compose up -d --build 才生效
- 数据库已在 Alembic 0001：docmind 与 docmind_test 都有 5 张业务表；跑完 pytest 要用 alembic 验库前，
  先 DROP SCHEMA public CASCADE; CREATE SCHEMA public; 再 upgrade head（否则 upgrade 是空操作）
- 迁移的两个硬约束：backend/alembic.ini 只能写 ASCII（本机 GBK 读它）；测试库连接串从 .env 派生，别抄口令

【第三步 当前状态】
- 停机点 2 已通过：周计划 10 组 35 项
- 第 1 组运行环境（1.1–1.6）+ 第 2 组数据模型与迁移（2.1–2.2）已完成，提交 98735be，工作区干净
- openspec list → 8/35 tasks；openspec validate --strict → valid
- pytest -q → 21 passed, 0 skipped；六个容器全 healthy，经 nginx 真请求 /health/ready 返回 200
- 下一项：第 3 组账号体系 —— 但它整组卡在停机点上，见下

【第四步 现在做什么】
第一步先出 ADR-0002（JWT 签发库 + 密码哈希库选型），写完停下等我批，不要自行选型。
选型前先读 docs/adr/0001-knowledge-base-entity.md 的写法，以及已就位的约束：
users.password_hash 是 VARCHAR(255)；配置里已有 JWT_ALGORITHM / TOKEN_EXPIRE_MINUTES / PASSWORD_MIN_LENGTH。
批准后再按 tasks.md 顺序：3.x 账号体系（含 1.5 遗留的双账号 fixture）→ 4.x 知识库 → 5.x 上传受理
→ 6.x 后台管线 → 7.x 状态与进度 → 8.x 重试与中断补偿 → 9.x 删除清理 → 10.x 验收留档。
若想利用等我批准的间隙：6.1（先写分块算法测试）零新依赖、不碰模型服务，但属跳步，需我先点头。

停机点提醒：
- 第 3 组整组阻塞：注册/登录需要 JWT 与密码哈希库，属"新依赖"，先出 ADR 等我批准
- 任何改 DDL / 改 Milvus collection schema 的动作同样先出 ADR
- 新增迁移文件只增不改；改结构要按第 2 组的验收方式（干净库 upgrade → downgrade → upgrade + alembic check）

【红线】
- 检索管线（分块/召回/RRF/重排/压缩）、mini-agent、引用对齐、语义缓存全部原生实现；
  禁 LangChain RAG 链、禁 LlamaIndex；LangGraph 只做编排
- 核心算法（分块 / RRF / 引用对齐 / 语义缓存）先写测试再实现
- 架构级决策（新依赖 / 改 DDL / 改 Milvus collection schema）先写 ADR，停下等我批
- 密钥不入 git；alembic/versions/ 只增不改；docs/task_plan.md 不虚构进度
- 所有查询必须带 user_id 过滤，文档与检索另加 kb_id 过滤
- 澄清问题必须我本人回答，禁止代答
- 不要用 /speckit.* 系列（已弃用），规格走 OpenSpec 主线
- skip 不等于通过：任何"依赖不可达就跳过"的用例，都要确认它真的 ran 过

【工程纪律（前两组踩出来的，务必遵守）】
- 同一文件的编辑必须串行执行，改完复核内容（同批并行编辑曾丢改动，导致 worker/beat 反复重启）
- docker compose ps 报 healthy ≠ 对链路可用，凡"通了"的结论必须打真实请求验证
- 分块验收按「覆盖性 / 顺序性 / 忠实性」三项判断，不得用"拼接结果等于原文"（与 64 token 重叠矛盾）
- 探测函数别把异常压成只剩类型名——第 2 组就因此把 Event loop is closed 误判成"测试库不可达"
- 声称"跑绿了"之前先看汇总行有没有 skip

【模型网关】
单一网关：一个 BASE_URL + 一个 API_KEY 覆盖生成/嵌入/重排三个用途。
两个坑：重排必须走 RERANK_BASE_URL（DashScope 原生路径，compatible-mode 下 404）；
生成模型默认思考模式，max_tokens 太小时 content 返回空串。详见 docs/HANDOFF.md 第六节。
W5 全程不调用任何模型服务。

【汇报要求】
- 中文；结论先行，不要套话与模板化铺垫
- 每完成一组任务给状态表格（任务 / 状态 / 验证证据）
- 声称"完成"必须能追到可复现的命令与输出，禁止凭印象下结论
- 每完成一组就回写 docs/progress.md 证据并勾选 tasks.md，不要堆到最后
```

## 变体 A：只推进某一项任务

```
你是 DocMind 项目的开发助手。先读 AGENTS.md、docs/HANDOFF.md，
再读 openspec/changes/add-doc-ingest-pipeline/tasks.md 中第 <组号> 组。

本次只做任务 <编号>：<任务描述>。
要求：
- 改动前先说明你打算怎么改，等我确认再动手
- 涉及核心算法先写测试
- 完成后给出：改了哪些文件、怎么验证的（命令 + 输出）、有没有偏离 tasks.md 原定验收
- 顺手把该项勾选与证据回写 tasks.md / docs/progress.md
环境注意：Bash 命令开头必须显式设 PATH（见 docs/HANDOFF.md 第三节）；
docker 命令需前置 /d/Docker/App/resources/bin；
如果这一项涉及新依赖 / 改 DDL / 改 Milvus collection schema，先停下出 ADR，不要动手实现。
```

```
你是 DocMind 项目的开发助手。先读 AGENTS.md 与 openspec/config.yaml。

我要变更的是：<描述改什么、为什么改>。
请走 OpenSpec 提案流：openspec new change <kebab-case 名>，然后按
openspec instructions <artifact> 依次产出 proposal / specs 增量 / design / tasks，
最后跑 openspec validate <change> --strict 并汇报结果。不要直接改代码。
若这次变更涉及新依赖、DDL 或 Milvus collection schema，先出 ADR 等我批准。

```
