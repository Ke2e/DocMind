# Feature Specification: 文档摄取管线（知识库 → 上传 → 异步解析 → 分块 → 进度可查 → 失败可重试）

**Feature Branch**: `001-doc-ingest-pipeline`

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 上传大文档不阻塞、进度可追踪 (Priority: P1)

作为知识库使用者，我把一份体积较大的文档（约 10MB 的 PDF）传到某个知识库后，希望立刻拿到"已受理"的反馈并可以继续操作，而不是卡在上传请求里；之后我能随时查到它处理到了哪一步（已接收 / 解析中 / 分块中 / 完成 / 失败），直到它变为"完成"。

**Why this priority**: 这是整个平台的地基。文档进不来、进来没状态，后面所有检索与问答都无从谈起；也是 W5 定义的核心验收项。

**Independent Test**: 向一个知识库上传约 10MB 的 PDF，记录接口返回耗时；随后按固定间隔查询该文档进度直到终态；验证进度序列单调推进、最终为"完成"且片段数量非零。单靠这一条即可交付可用的 MVP（文档进库）。

**Acceptance Scenarios**:

1. **Given** 已登录且已存在一个知识库，**When** 提交一份约 10MB 的 PDF，**Then** 请求在秒级内返回"已受理"与文档标识，期间服务仍能正常响应其他请求
2. **Given** 文档正在处理中，**When** 反复查询该文档进度，**Then** 每次都返回当前所处阶段，且阶段按既定状态机单调推进，不出现回退
3. **Given** 文档处理完成，**When** 查询该文档详情，**Then** 状态为"完成"、片段数量大于 0，且片段内容与原文一致
4. **Given** 文档处理中出现异常，**When** 查询进度，**Then** 返回可读的阶段与失败信息，而不暴露原始堆栈或内部错误细节

---

### User Story 2 - 用知识库归类文档 (Priority: P1)

作为用户，我可以创建多个知识库（例如"课程笔记""产品手册"），上传文档时必须把它放进其中一个知识库；列表与进度也能按知识库筛选，不同知识库的内容互不串台。

**Why this priority**: 上传入口必须知道文档归属哪个知识库，它位于主链路上；数据模型一旦定错，后续检索过滤条件与前端都要返工。

**Independent Test**: 创建两个知识库，分别上传文档，按知识库查询列表与文档详情，确认各自只返回本库内容。

**Acceptance Scenarios**:

1. **Given** 已登录用户，**When** 创建一个知识库，**Then** 该知识库出现在自己的知识库列表中，名称重复时被拒绝或自动区分
2. **Given** 已有两个知识库，**When** 分别上传文档，**Then** 每份文档的归属知识库与上传时指定的一致，按任一知识库筛选列表只返回本库文档
3. **Given** 某知识库下已有文档，**When** 用户尝试删除该知识库，**Then** 删除被拒绝并提示该库下仍有文档（需先清空）
4. **Given** 一个空的知识库，**When** 用户删除它，**Then** 删除成功且不再出现在列表中

---

### User Story 3 - 只能看到自己知识库里的文档 (Priority: P1)

作为注册用户，我希望知识库、文档列表、进度、详情、删除等操作都只作用于我自己的数据；别人的知识库与文档我既看不到也操作不了。

**Why this priority**: 数据隔离是安全底线，一旦在第一个增量里没做扎实，后续所有功能都要返工补过滤条件。

**Independent Test**: 用两个账号分别建知识库并上传文档，交叉访问对方的知识库标识与文档标识，全部被拒绝或返回不存在；各自列表只含自己的数据。

**Acceptance Scenarios**:

1. **Given** 用户 A 与用户 B 各有知识库与文档，**When** A 查询知识库或文档列表，**Then** 结果只包含 A 自己的数据
2. **Given** 用户 A 已知用户 B 某知识库或文档的标识，**When** A 直接查询、上传到或删除该对象，**Then** 被拒绝且不泄漏其内容
3. **Given** 未携带有效凭证，**When** 调用任一知识库或文档接口，**Then** 被拒绝并提示需要登录

---

### User Story 4 - 坏文件明确失败且可重试 (Priority: P2)

作为用户，当我上传了损坏或不支持的文件时，我希望看到人话写的失败原因，并且在我修好之后能一键重跑，而不是只能删掉重传。

**Why this priority**: 直接影响可用性，但不阻塞"好文件能进库"这条主链路，故列 P2。

**Independent Test**: 上传一个内容损坏的文件，观察其自动重试后最终标记为"失败"并携带可读原因；再次手动重试，状态回到处理流程起点；换修复后的文件重试则走到"完成"。

**Acceptance Scenarios**:

1. **Given** 上传了无法解析的损坏文件，**When** 管线处理它，**Then** 系统自动重试至多 2 次，随后文档标记为"失败"并附带可展示给用户的失败原因
2. **Given** 文档处于"失败"状态且手动重试次数未达上限，**When** 用户触发重试，**Then** 文档重新进入处理流程，状态回到起始阶段，可重新走完整个状态机
3. **Given** 自动重试与手动重试次数均达上限，**When** 再次请求重试，**Then** 系统给出明确限制提示而非无限重跑
4. **Given** 处理中的任务因后台进程重启而中断，**When** 用户查询进度，**Then** 该任务被识别为异常中断并可被重新调度，而不是永远卡在处理中

---

### User Story 5 - 删除文档及其派生数据 (Priority: P3)

作为用户，我希望删除文档时它产生的所有片段与中间产物一并清掉，不留下孤儿数据。

**Why this priority**: 属于数据生命周期闭环，可在主链路稳定后补齐。

**Independent Test**: 上传文档待其完成后删除，再查询其片段与详情，确认全部不可访问；删除后该文档不再计入所属知识库的文档数。

**Acceptance Scenarios**:

1. **Given** 文档处于"完成"状态，**When** 用户删除它，**Then** 文档及其全部片段不可再被查询到
2. **Given** 文档正在处理中，**When** 用户删除它，**Then** 删除立即生效，后台任务随即中止且不再写入该文档的数据

---

### Edge Cases

- 上传 0 字节文件或空文档
- 上传超出 50MB 上限的文件
- 上传格式不在支持列表（PDF / DOCX / MD / TXT）内，或扩展名与实际内容不符（如 .pdf 实为图片）
- 上传无文本层的扫描版 PDF（无 OCR，应失败并给出可读原因）
- 上传加密 / 需要口令才能打开的文档
- 同一用户重复上传同名文件（按新文档处理，不覆盖，见 Assumptions）
- 同一用户连续上传两个内容完全相同的文件（允许，视为两份独立文档）
- 上传成功后立刻查询进度，此时后台任务尚未被领取
- 后台处理进程在处理中途被停止或崩溃
- 用户在文档处理中发起删除
- 同一用户并发上传多个文档到同一或不同知识库时，进度相互独立
- 知识库重名、知识库名为空或超长
- 删除仍含文档（含正在处理中文档）的知识库
- 超长单页、无换行、表格密集等极端版式导致的解析异常

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 允许已登录用户在指定知识库下提交文档文件，并立即返回受理结果与文档标识，不等待解析完成
- **FR-002**: 系统 MUST 在后台异步完成"解析 → 清洗 → 分块"的处理链路，不占用处理用户请求的线程
- **FR-003**: 系统 MUST 为每份文档维护可查询的处理状态，状态覆盖：已接收、解析中、分块中、完成、失败（并保留"向量化"阶段位供后续启用）
- **FR-004**: 系统 MUST 提供按文档查询进度的能力，返回当前阶段与已完成的阶段信息
- **FR-005**: 系统 MUST 在文档处理完成后持久化其片段内容与顺序序号，并可通过文档反查全部片段
- **FR-006**: 系统 MUST 支持分块粒度与重叠比例的配置化调整，调整无需修改代码
- **FR-007**: 系统 MUST 在文档处理失败时记录可读的失败原因，并通过接口返回给用户
- **FR-008**: 系统 MUST 对处理失败自动重试，最多 2 次且相邻重试之间带退避等待
- **FR-009**: 系统 MUST 允许用户对失败文档发起手动重试，手动重试次数设有上限；自动与手动重试合计达上限后不再重跑
- **FR-010**: 系统 MUST 允许用户创建、列出、重命名、删除自己的知识库
- **FR-011**: 系统 MUST 保证每份文档必须且只能归属一个知识库，未指定归属的提交被拒绝
- **FR-012**: 系统 MUST 拒绝删除仍含文档（含处理中文档）的知识库，并提示未被清空的文档数量
- **FR-013**: 系统 MUST 保证所有知识库、文档、进度、片段的查询与操作都按用户维度过滤；且按知识库维度筛选时结果不跨库
- **FR-014**: 系统 MUST 在删除文档时一并清除其全部派生数据（片段与处理记录）
- **FR-015**: 系统 MUST 拒绝体积超过 50MB 或格式不在支持列表（PDF / DOCX / MD / TXT）内的文件，并在提交阶段给出明确提示，不产生半成品文档记录
- **FR-016**: 系统 MUST 对同一文档的处理保持幂等：重复投递同一处理请求不产生重复片段
- **FR-017**: 系统 MUST 识别因后台进程异常中断而长期停留在中间状态的任务，并支持重新调度或标记为失败
- **FR-018**: 系统 MUST 记录文档的基础属性（原始文件名、类型、字节大小、状态、失败原因、片段数量、归属知识库、创建时间）供列表展示
- **FR-019**: 系统 MUST 拒绝创建重名或非法（空名 / 超长）的知识库，或按明确规则自动区分

### Key Entities *(include if feature involves data)*

- **Account（账号）**: 平台使用者身份，是知识库与文档的归属维度
- **Knowledge Base（知识库）**: 用户创建的内容容器；属性包括名称、描述、归属用户、创建时间；一个用户可有多个知识库，是文档归属与检索过滤的一等维度
- **Document（文档）**: 用户上传的一份原始文件；属性包括原始文件名、存储位置、文件类型、字节大小、处理状态、失败原因、片段数量、**归属知识库**、创建时间；生命周期遵循"已接收 → 解析中 → 分块中 → 完成 | 失败"，失败态可回到起点
- **Chunk（片段）**: 文档切分后的文本单元；属性包括所属文档、顺序序号、文本内容、长度计量；随文档删除而级联移除
- **Processing Task（处理任务）**: 一次文档处理的执行记录；属性包括关联文档、当前阶段、自动重试次数、手动重试次数、最近一次执行时间；用于支撑进度查询、重试与中断识别

> 向量化所需的向量记录本次只预留位置、不落数据；002 接入时向量集合需带知识库维度以支持过滤（见 ADR-0001 影响面）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 提交一份约 10MB 的文档，用户在 2 秒内拿到受理结果，且提交过程中服务对其他请求的响应无明显变慢
- **SC-002**: 一份约 10MB（约 200 页量级）的文档，从提交到变为"完成"状态耗时控制在 5 分钟以内
- **SC-003**: 处理全过程任意时刻查询进度，返回阶段与真实执行状态一致，能支撑展示一条连续的进度
- **SC-004**: 跨用户、跨知识库越权访问与操作的尝试，100% 被拒绝
- **SC-005**: 损坏或不支持的文件在提交后 60 秒内（含至多 2 次自动重试）被标记为"失败"并给出可读原因；触发手动重试后能重新进入处理流程
- **SC-006**: 处理完成的文档可被后续检索环节完整取用：片段内容忠实于原文、顺序可还原，无缺段、无重复段
- **SC-007**: 分块粒度与重叠比例可在不改动代码的前提下调整，调整后新处理的文档立即生效
- **SC-008**: 同一用户可维护多个知识库；按知识库筛选列表与进度时，返回结果与筛选条件 100% 一致，不跨库、不漏库
- **SC-009**: 4 种支持格式（PDF / DOCX / MD / TXT）各上传一份样例，均能走到"完成"且片段可还原

## Assumptions

- 目标使用者为单人名下使用，团队 / 空间级共享属后续增量
- 文档内容以可提取文本为主，扫描件 OCR 不在本期（无文本层时按失败处理）
- 本期验收以接口与自动化测试为主，不交付完整前端界面
- 状态机中"向量化"阶段位只预留不启用，文档分块完成后即视为"完成"（002 接入向量库）
- 进度获取采用调用方按需查询的方式，不引入长连接推送（后续增量已有流式通道规划，可复用）
- 单账号知识库数量、文档数量与总存储量在首版不设硬性配额
- 重试上限：自动 2 次（指数退避），手动至多 3 次；合计上限在配置中可调
- 同名文件重复上传按**新文档**处理，不覆盖已有文档，列表以创建时间区分
- 分块默认粒度 512 token、重叠 64 token，参数可配置（保护清单要求原生实现，参数外置）
- 知识库删除采用"非空则拒绝"策略，不做级联删除
- 服务以容器化方式整体启动，运行依赖与密钥在开工前由开发者本地准备就绪
- 代码与规格直接放在仓库根目录，不再额外嵌套一层项目目录

## Dependencies

- 容器化运行环境（应用 / 后台执行 / 关系库 / 缓存 / 反向代理）可一键启动且健康检查通过
- 开发者本地提供文档解析所需的运行配置与访问密钥
- 验收语料：4 种支持格式各一份样例 + 一份刻意损坏的文件 + 一份无文本层扫描件
- 既有账号体系（沿用 OneHub 的表结构与认证方式）
- **DDL 变更（已批准）**：`knowledge_bases` 新表与 `documents.kb_id` 字段 —— ADR-0001 于 2026-09-12 获开发者批准，随 W5 落地（迁移为新增文件）

## Out of Scope

- 问答与检索链路（问题改写、召回、重排、生成、流式输出）
- 向量化与向量库写入（002 增量）
- 引用溯源与前端界面
- 多轮会话与消息持久化
- 语义缓存、评测体系与参数测试台
- 团队 / 空间级多租户与知识库共享
- 图片型扫描件识别（OCR）
- 知识库级配额与计费
