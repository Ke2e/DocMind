## Context

动机与范围见 `proposal.md`。本设计只记录"怎么做"层面的约束与取舍。

当前状态：仓库里只有规格与规划文档，没有代码。OneHub 项目已完成，其 FastAPI 应用骨架、Celery 出栈、Redis 用法、SSE 通道都是现成经验，可直接复用模式（不复制代码）。

既有限制：

- 技术栈已锁定（constitution 原则 II）：Python 3.12 + FastAPI + Pydantic v2 + SQLAlchemy 2.0(async) + Alembic + PostgreSQL 16 + Celery/Redis，部署走 Docker Compose
- 分块算法属保护清单（constitution 原则 I），必须原生实现，禁止 LangChain / LlamaIndex 的分割器
- 里程碑纪律：本增量只到"分块完成"，向量化与问答留 002

## Goals / Non-Goals

**Goals:**

- 一个可一键启动的容器化运行环境，能支撑"API 层接收、执行层处理"的分离
- 一份可迁移、可回滚的 DDL 变更（新增知识库维度）
- 一条端到端可验收的摄取链路：提交 → 后台解析/清洗/分块 → 状态可查 → 失败可重试 → 删除可清理
- 核心算法（分块）有测试覆盖，重试与中断补偿有可复现的证据

**Non-Goals:**

- 不追求吞吐与并发调优（本期只验证"不阻塞"）
- 不引入对象存储：文件落在挂载卷上即可
- 不做 OCR、不做扫描件识别
- 不做前端界面（验收走接口与自动化测试）
- 不启用向量库写入（Milvus 容器可起，但不进入数据流）

## Decisions

### D1. 复用 OneHub 的脚手架形态，而非从零搭

直接照搬 OneHub 已验证的分层（`core/` 配置与客户端、`api/` 路由、`services/` 领域逻辑、`models/`/`schemas/` 分离、`workers/` 出栈任务）。**备选**：从零新建结构 —— 被否，W5 时间预算不支持重复验证已知结构。

### D2. 解析/分块在 Celery 执行层完成，任务记录落 PostgreSQL 而非只存 Redis

API 进程只做校验、落库、投递任务、立即返回；解析与分块在 worker 中执行。进度状态**持久化到 PostgreSQL**（`documents.status` + 处理任务记录），Redis 只用于 broker 与短期状态。**备选**：`BackgroundTasks`（进程内、不可扩容、进程重启丢任务，且违反 FR 的"不占用请求线程"精神）；**备选**：状态只存 Redis（重启丢状态、无法支撑"中断任务可识别"的验收）。

### D3. 状态与尝试次数分两处存

`documents.status` 存当前阶段（供列表与进度查询，读多写少）；独立的处理任务记录存"自动重试次数 / 手动重试次数 / 最近一次执行时间"。**理由**：重试计数与补偿扫描需要独立的时间维度，混进文档表会让状态机与计数互相污染。**备选**：单表堆字段 —— 被否，删除文档时想要"级联清理处理记录"就得靠手工清字段。

### D4. 幂等靠数据库唯一约束兜底，而不是靠"先查再写"

片段表对 `(document_id, chunk_index)` 建唯一约束；重试或重复投递在写入前于同一事务内先清空该文档已有片段再写入。**备选**：应用层先查后写 —— 有竞态，且无法防御 worker 被重复投递。

### D5. 分块算法原生实现（保护清单）

按 `\n\n` → `\n` → 句末标点逐级降级的递归分割，目标粒度与重叠比例外置到配置（默认 512 / 64 token），计数用 tiktoken。参数改动不需要改代码，符合 FR 与 SC 的要求。**TDD 要求**：先写测试（边界：空文档、单段超长无标点、表格密集、恰好等于粒度、极小文档）。

**重叠语义（2026-09-12 补充）**：重叠指相邻片段共享边界文本，因此片段集合必然包含重复文本。SC-006 的"无缺段、无重复段"据此解释为"无内容缺失、无重复片段"（不存在内容完全相同的两个片段），而非"文本不重复"。内容忠实性以三项校验：覆盖性（原文每个 token 位置至少被一个片段包含）、顺序性（按 `chunk_index` 升序与原文顺序一致）、忠实性（每个片段是原文的连续子串）。**不得以"拼接结果等于原文"为判据**——该判据与重叠参数直接矛盾。

### D6. 重试采用"自动少量 + 手动兜底"

自动重试由执行层自带的失败重试机制完成（上限 2 次、指数退避）；手动重试 = 校验上限 → 重置状态与阶段 → 清理旧片段 → 重新投递。**理由**：瞬时故障（IO、外部依赖抖动）自动消化，确定性错误（坏文件）交给用户判断，避免无限重试浪费算力。

### D7. 中断补偿用定时扫描

beat 周期扫描"停留在中间阶段且最近执行时间超过阈值"的处理记录，重新调度或标记失败。**备选**：只靠任务超时 —— 被否，"永久卡在处理中"是明确列入验收的负例。

### D8. 删除语义：文档级联清、知识库非空拒删

文档删除走数据库级联（片段随文档删除）；删除中的文档引入"待删/已删"标记，worker 每次写入前校验该标记，避免"用户已删、worker 又写回"。知识库删除在应用层校验非空即拒，不做级联。**理由**：级联删知识库会与正在执行的 worker 产生竞态（见 `docs/adr/0001`）。

### D9. 文件落挂载卷，Docker Compose 统一编排

上传文件写入挂载卷（api 与 worker 共享），元数据落 PostgreSQL。**备选**：MinIO —— 本期 Milvus 依赖的 minio 实例不与应用文件混用，引入独立对象存储属于新增依赖，推迟到确有需要时再走 ADR。

**宿主端口约束（2026-09-12 实测）**：本机宿主 8000 / 5432 / 6379 已被在跑的 OneHub 栈占用，9000-9001 / 9091 / 19530 被其 Milvus 占用。故 compose 使用独立 project name `docmind`，pg / redis / nginx 分别映射到 **5433 / 6380 / 8080**，api 容器内端口不对宿主暴露；两套栈必须能同时运行。

### D10. 统一错误响应契约与测试脚手架（第 1 组交付的基础设施）

错误响应统一为 `{code, message, detail?}`：`code` 机器可读、`message` 面向用户可读、`detail` 可选补充；由全局异常处理器产出，并覆盖框架默认的 404 / 422。**理由**：进度与失败信息的接口要求"不暴露堆栈与内部实现细节"，没有统一出口就无法在每处保证，且前端需要稳定的错误形状。

测试脚手架为 pytest + pytest-asyncio + httpx `AsyncClient`，`conftest` 负责测试库 schema 建 / 销毁与双账号 fixture；接口测试不依赖已启动的 worker（任务投递在测试中替换为记录桩）。**理由**：分块算法要求 TDD 先写测试，第 3–5 组的验收方式全是接口测试——脚手架属第 1 组必须交付的基础设施，否则后续任务的"验证方式"无处落地。

## Risks / Trade-offs

- [大文件把 worker 内存打满] → 流式/分页读取解析，按文档粒度处理，单 worker 并发受限
- [删除与写入竞态导致孤儿片段] → 删除标记 + 写入前校验；片段写入与状态更新放同一事务
- [重试叠加导致同一文档被并发处理] → 投递前加分布式锁（复用 Redis），并靠唯一约束兜底
- [compose 里 Milvus 全家桶在 Windows 上吃内存] → 用 compose profile 把 Milvus 相关容器列为可选，本期默认不启动
- [DDL 变更不可逆] → Alembic 新增版本并提供 downgrade；先在干净库上验证 upgrade/downgrade 再合入
- [状态机被绕过：直接改库改状态] → 所有状态迁移收敛到单一 service 方法，测试覆盖非法迁移

## Migration Plan

1. **DDL 先行**：生成 Alembic 迁移（新增文件，不改历史版本），在干净库上验证 `upgrade` 与 `downgrade`
2. **环境起容器**：先起 PostgreSQL / Redis，再起 API 与执行层；确认健康检查通过
3. **功能合入顺序**：账号 → 知识库 → 上传受理 → 后台管线 → 进度 → 重试/补偿 → 删除
4. **回滚**：功能层面按提交回退；数据层面执行 `downgrade`（本期无存量数据，回滚风险低）
